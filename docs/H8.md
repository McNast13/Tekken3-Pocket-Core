# The H8/3002 for Tekken 3: design and checking

System 12's H8/3002 runs the sound program (`tet1vere.11s`, 512 KB) and reads the controls. It drives the C352 at
0x280000, talks to the main CPU through the shared RAM at 0x080000-0x083FFF (the main CPU's 0x1F080000), and reads the
inputs at 0x300000. The core has a fake H8 for now (docs/CORE_T3.md); this is the plan for the real one, for sound
(first) and then controls.

## Reference: MAME, recorded and replayed

- `tools/mame/h8_ref.lua` records MAME's H8: an instruction trace from power-on with ER0-ER7 and CCR (30 frames,
  1.46M instructions), a 60 s log of its outside accesses, a RAM snapshot where the trace's registers begin, and every
  outside read after that point. Output in `tests/h8/ref/` (git-ignored: derived from the ROMs).
- `tools/h8model/` is a Python H8/300H generated from MAME's own H8 description (`h8.lst`, `h8.cpp`, BSD-3,
  vendored): `h8gen.py` translates it, `h8cpu.py` runs it, `h8check.py` replays the recording. Result (2026-11-14): all
  1,402,032 recorded instructions match MAME (PC, ER0-ER7, CCR before each), with 145 interrupts and 11,115 outside
  reads replayed. It is the reference for the VHDL CPU and a source of random instruction tests.
- Coverage so far: the first 30 frames (boot), 52 different instructions. A second recording during the attract
  music, when the sound program is busiest, comes before the CPU is called finished.

## What the program uses (MAME, 60 s of attract mode)

- 138,000 reads per frame (instruction fetches included). The 16 hottest 64-byte ROM lines (1 KB) take 80% of them:
  the polling loops.
- ROM: 371 lines (23 KB) read in 60 s, between 0x000000 and 0x0321BF; 184 of them first read after 10 s (the music's
  data). RAM: 256 lines (16 KB) read.
- C352 register writes: about 120 a second at boot, up to about 4,800 a second with the attract music.
- On-chip peripherals written: the 16-bit timer unit (0xFFFF60-0xFFFF97, the tempo interrupts), SYSCR (0xFFFFF2 = 0x03:
  UE = 0, so an interrupt sets I and UI), and a few port and bus registers. DMA registers are not used.

## Plan for the core

| Part | How | Block RAM |
|---|---|---|
| CPU | H8/300H, advanced mode, multi-cycle; not cycle-exact (the program's timing comes from the timer interrupts, not instruction counts) | register file |
| ROM | 512 KB in SDRAM (the H8 program slot), read through a 16 KB direct-mapped cache; holds the whole 60 s working set | ~14 M10K |
| RAM 0x080000-0x083FFF | the existing 32 KB shared mailbox RAM (`c76_sound`), the H8 on its byte port | (exists) |
| RAM 0x084000-0x08FFFF | 48 KB, H8 only | ~39 M10K |
| On-chip RAM 0xFFFD10-0xFFFF0F | 512 B | 1 M10K |
| Peripherals | timer unit, interrupt controller, SYSCR, ports (sized in synth/h8_size: 642 ALMs, next to a CPU model of 1,182) | |
| Outside | C352 at 0x280000 (the existing one), inputs at 0x300000, wait-state writes ignored | |

About 55 M10K of the ~178 free. ALMs: the real CPU 2,006 (h8_cpu_size), peripherals ~650-750 and glue ~150-300
(synth/h8_size models), about 2,800-3,050 in all, of ~4,150 usable (t3fps1 at 14,140 of 18,480; LABs run out
near 18,300).

## Order

1. CPU in VHDL, checked in nvc against the same replay as the Python model (the testbench emits the trace format;
   a script compares). Then random instruction tests against the Python model, for instructions the recordings miss.
2. Second MAME recording during the attract music; replay it.
3. Timer unit and interrupt controller, checked against MAME's timer register reads and interrupt points.
4. Into the core in place of the fake H8: the H8 program data slot and loader, the ROM cache on SDRAM, the RAMs, the
   C352. First milestone on the Pocket: attract mode with sound.
5. Controls through the H8 (0x300000 inputs).

## Status (2026-11-15)

- `pocket/core/s12/h8_alu.vhd`: 200,000 random cases against the generated MAME helpers, 0 errors (tests/h8/alu;
  three planted bugs all caught).
- `pocket/core/s12/h8_cpu.vhd` (reworked 2026-11-15 for size and speed): a fixed datapath (two register read ports,
  one address adder, one ALU, one multiplier with a registered product, a one-bit-per-clock divider, one register
  write port) steered by small select codes; a two-word prefetch queue that a taken branch flushes; posted writes.
  - Checks: all 1,402,032 instructions of the Tekken 3 recording match MAME (tests/h8/cpu); random straight-line
    programs, 91 instruction kinds, match the model in registers, flags and RAM (tests/h8/rand/make_rand.py: 6 seeds,
    270,006 instructions); random control flow - Bcc d8/d16, bsr, jsr and jmp in every addressing form, rts, trapa
    with rte, loops - matches too (tests/h8/rand/make_flow.py: 3 seeds, 37,626 instructions, stack RAM checked).
    Planted bugs (trapa stacking its own address, a flushed prefetch not discarded) are caught.
  - Size and timing, alone (synth/h8_size, `run.sh h8_cpu_size`): 2,006 ALMs, 709 registers, 1 DSP; timing met in all
    four models at 33.8688 MHz (worst setup +2.46 ns Slow 85C, worst hold +0.122 ns Fast 0C; Fmax 36.95 MHz). The
    first version of this CPU was 7,074 ALMs and failed setup by 84 ns: four one-clock 32-bit dividers (~2,600 ALMs)
    and operand selectors built at every use.
  - Speed with a one-clock memory: 4.75 clocks per instruction outside the idle loop (the replay; first version
    10.3), 3.2 on random straight-line code. A fight's busiest 1/60 s in MAME is about 37,000 working instructions
    (see below): about 176,000 of the frame's 564,000 clocks.
- `pocket/core/s12/h8_periph.vhd` (2026-11-15): the on-chip peripherals Tekken 3 uses, after MAME 0.289's H8/3002
  devices (vendored in tools/h8model/mame: h83002, h8_timer16, h8_intc, h8_adc, h8_sci, h8_port; BSD-3): timer
  channels 0-3 (channels 0 and 1 overflow at 120 Hz: the tempo; 2 and 3 are free-running time-outs), IRQ0-5 and the
  priority / I-UI masking, the A/D converter (started by the end of vblank on ADTRG; the program waits for it every
  frame), SCI1 in clocked synchronous mode (the settings / RTC link; its reads time out), ports, SYSCR. Left out: timer
  channel 4 and its PWM / buffer modes, A/D scan mode, SCI0 beyond its registers (JVS, unused), DMA, watchdog.
- System test, tests/h8/sys (run.sh FRAMES): CPU and peripherals boot Tekken 3's H8 program from reset; the main
  CPU's shared-RAM writes recorded by tools/mame/h8_shared.lua (MAME with an initialised NVRAM) are played back at
  their frames; the C352 is modelled as MAME's (registers, key-on / key-off on the 0x280404 write; the 6 sample ends
  in 16 s come from MAME's recording). Every C352 write is compared with MAME's: per register the same value sequence,
  and within 2 frames of MAME's time. Result, 16 s (960 frames; the attract music starts at 10 s): all 13,408 writes
  to 160 registers match, all within 0 to -1 frame. A planted bug (timers at phi/4 instead of phi/8) fails it (768
  writes off time). 16 s takes about 10 minutes in nvc.
- CPU and peripherals together (synth/h8_size `run.sh h8_sys_size`): 2,840 ALMs, 1 DSP; timing met in all four
  models (worst setup +2.93 ns Slow 0C, worst hold +0.126 ns Fast 0C). Still to add for the whole H8: the ROM cache,
  RAMs and bus glue (~150-300 ALMs, ~55 M10K).
- MAME, how busy the H8 is (instructions outside the polling loop at 0x158A, per 1/60 s of MAME's instruction stream):
  attract mode up to 35%; a coin-up fight (stages 1-3, P1 pressing buttons) 19-28% on average, up to 78% in the
  busiest 1/60 s, with up to 21,000 instructions between polls.
- Deliberate differences from MAME, where its H8 core disagrees with Hitachi's H8/300H manual (the core follows the
  manual; none of these instructions appears in the recording so far):
  - divxu.w sets N from the divisor's bit 15 (MAME: bit 7);
  - trapa stacks the address of the next instruction (MAME stacks the trapa's own address, so its rte would trap again).
  - (Correction, 2026-11-15: an earlier version of this list said MAME's trapa leaves CCR alone. MAME's generic
    h8.lst does, but its H8/3002 device sets I, or I and UI, in trapa_setup, as the manual and the core do. Only the
    Python model, generated from h8.lst without that override, differed; tests/h8/rand/make_flow.py corrects it.)
